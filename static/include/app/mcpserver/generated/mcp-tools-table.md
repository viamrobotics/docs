| Tool | Category | Description |

| `get_registry_item_information` | Read-only | Look up the registry documentation for a Viam resource model. Given a resource's api and model — from read_machine_config, read_fragment_config or search_configuration_blocks — returns the module that provides it: the module's description and documentation, plus the model's own description and documentation, which is where its configuration attributes are described. Use it to learn how to configure a specific component or service model, and prefer it over a web search for registry models. |
| `list_machines` | Read-only | List the machines you can access and get the machine id other tools need. Call it with no arguments for the whole fleet, or pass name to filter: case and separators do not matter and partial names match, so pass the machine name alone rather than a sentence. Scope with organization_id or location_id only when the user named one. Machines come back most recently online first, or best name match first when name is given. Pick the machine the user meant out of the results yourself, and ask them only when it is genuinely ambiguous. When truncated is true more machines exist than are listed, so filter by name or scope to an organization rather than treating the list as complete. |
| `list_organization_locations` | Read-only | List the locations in an organization and get the location id that list_machines takes as location_id. Takes the organization id, from list_organizations. Every location the organization can see is listed, the ones it owns and the ones other organizations share with it alike; primary_organization_id names the owner. A nested location names its parent as parent_location_id. Locations come back in name order. When truncated is true more locations exist than are listed, so say so rather than treating the list as complete. |
| `list_organizations` | Read-only | List the Viam organizations you can access. Start here when you need an organization id; machine and part ids come from list_machines. |
| `read_fragment_config` | Read-only | Read a fragment's configuration: given a fragment id (from search_configuration_blocks), returns the fragment's config exactly as saved — the same config the fragment editor shows — plus the fully-resolved contents of each fragment that config imports (nested fragments inlined, variables substituted, prefixes applied), since an import contributes resources the config alone does not show. A fragment that cannot be resolved reports its error inline instead. Reads the latest version unless version names a revision or a release tag. |
| `read_inline_module_code` | Read-only | Read the source code of an inline module: a module whose code is written in the builder's inline module editor and hosted by Viam (also called control code). Given the module's id — the module_id of its entry in a config's modules list, from read_machine_config or read_fragment_config — returns the file the editor edits (src/models/generic_service.py for Python, module.go for Go) as last saved. Each save is a source revision N, built as module version 0.0.N: a config that pins the module to 0.0.N runs that revision, and one pinned to latest runs the newest build. Reads the latest revision unless version names an earlier one. Edits not yet saved in the editor are not visible here. A module whose source is not hosted by Viam is refused; get_registry_item_information has its documentation. |
| `read_machine_config` | Read-only | Read a machine's configuration: given a machine id (from list_machines), returns every part of the machine with its config exactly as saved, plus the fully-resolved contents of each fragment the config imports (nested fragments inlined, variables substituted, prefixes applied), since an import contributes resources the config alone does not show. A fragment that cannot be resolved reports its error inline instead. Most machines have a single part; on a multi-part machine each part is its own config. |
| `read_machine_logs` | Read-only | Read a machine part's most recent logs, newest first — use it to investigate an error the user reports, or to check whether a component or service started cleanly. Reads one part at a time: omit part_name for the machine's main part, or name another part (the result lists the machine's other parts). Narrow the read with levels — pass error and warn to look for problems — and with filter, a case-insensitive substring such as a component's name. Only the last 24 hours are covered, and only logs the machine reports to the cloud: a machine that has been offline longer, or has never connected, has nothing to return. Read the machine's config with read_machine_config to find the resource and part a log line is about. |
| `read_part_status` | Read-only | Check whether a machine part is online, offline or awaiting setup, which means it has never connected to Viam. Reads one part at a time: omit part_name for the machine's main part, or name another part (the result lists the machine's other parts). Online means the part reported to Viam within the last 10 seconds; an offline part comes with when it was last online and for how long it has been offline. Use it to tell the user whether their machine is live, for example after configuring it, to explain why read_machine_logs returned nothing, or before run_docommand and call_machine_api, which need the part online. This is Viam's record of the part's connectivity, not the state of its resources: for those, call GetMachineStatus with call_machine_api once the part is online. |
| `read_viam_docs` | Read-only | Search the official Viam documentation and return the most relevant passages with their source URLs. Use it to look up how Viam works — concepts, components and services, the machine config schema, integrations, and how-to guides — and cite the URLs it returns. Prefer it over a web search for anything the Viam docs cover; it is faster and more precise. Passages are capped, and total_result_count reports how many matched. |
| `search_configuration_blocks` | Read-only | Search the Viam registry and fragments for configuration blocks — components and services (registry module models) and fragments — that could be added to a machine's configuration. Use it both for a specific part (e.g. "Raspberry Pi 5 board", "intel realsense camera") and for a vague need (e.g. "camera", "arm"). Returns the best matches with each module's api/model pairs and each fragment's name and id; a module's matched_model_count is absent when the module matched as a whole, in which case models is just its catalog. Only public blocks are searched unless you pass organization_id, which adds that organization's own private and unlisted ones if you can read its private registry items. Results are capped, and total_result_count reports how many matched. |
| `add_fragment_config_item` | Write | Add one item to a fragment's configuration and save it, the way the fragment builder's Add menu does. The save is immediate and becomes the fragment's latest revision, which every machine importing the fragment without a pinned version picks up, so be sure the user wants the change, and read the fragment with read_fragment_config first. Given the fragment id, adds a named resource (component, service, registry_module, remote, trigger, job) or a fragment import (fragment, naming the fragment to import in import_fragment_id), one per call; the result shows the item exactly as saved. The items and their rules are add_machine_config_item's, with the fragment in place of the part: a component's or service's model is checked against the registry and the module providing it is added when missing (pass module_id to choose it, or to name one already on the fragment), a remote takes an address, a job's resource or a conditional trigger's component_name must be a component or service on the fragment or one of its imports, a trigger needs an event_type and at least one notification, and names must be unique on the fragment, counting the resources its imports provide. Unlike a machine, a fragment may leave an import's variables unset, for the machine importing this fragment to set; the result lists them. A fragment cannot import itself, directly or through its imports. This tool only adds: it never changes or removes an item that exists. |
| `add_machine_config_item` | Write | Add one item to a machine part's configuration and save it, the way the builder's Add menu does. The save is immediate — there is no draft — so be sure the user wants the change, and read the part's config with read_machine_config first. Given the machine id (from list_machines) and, on a multi-part machine, a part name, adds a named resource (component, service, registry_module, remote, trigger, job) or a fragment import (fragment), one per call; the result shows the item exactly as saved. For a component or service, take the api and model from search_configuration_blocks or get_registry_item_information: the model is checked against the registry, and the module providing it is added to the part when missing (pass module_id to choose the module, or to name one already on the part, such as a module hot-reloaded with viam module reload, which is then trusted to provide the model; an rdk model is built in and needs none). A remote takes the address of the machine to connect to. A job's resource or a conditional trigger's component_name must be a component or service already on the part or one of its fragments. A trigger needs its event_type — part_online, part_offline, part_data_ingested, conditional_data_ingested or conditional_logs_ingested — and at least one email or webhook notification; two triggers must not notify one recipient for the same event unless seconds_between_notifications is 0, since they would share a cooldown and only one would fire. A fragment import must be given a value for every variable the fragment uses. Names must be unique on the part, counting the resources the fragments it imports provide. This tool only adds: it never changes or removes an item that exists. |
| `create_fragment` | Write | Create a new, empty fragment — a reusable piece of machine configuration that machine configs import — owned by an organization, the way the app's New fragment dialog does. Takes the organization id (from list_organizations), a name unique among that organization's fragments, and optionally a visibility: private (the default; only the organization can see or use it), public_unlisted (usable by anyone who has the fragment id) or public (listed for everyone); both public kinds require the organization to have a public namespace. The fragment is created with an empty config: add items to it with add_fragment_config_item, or in the fragment builder in the Viam app, at the url returned. Read it back with read_fragment_config. |
| `create_machine` | Write | Create a new machine in a location, the way the app's Add machine dialog does. Takes the location id (from list_organization_locations) and a name unique among that location's machines, ignoring case. The machine belongs to the organization that owns the location and starts with one part, named after it with -main, whose config is empty unless the organization has default fragments, which it then imports. Add items to its config with add_machine_config_item, or in the machine's builder in the Viam app, at the url returned, which also has the setup instructions for running viam-server as the machine on hardware. Read the config back with read_machine_config. |

| `update_fragment_config_item` | Write (destructive) | Change one item in a fragment's configuration and save it, the way editing it in the fragment builder does. The save is immediate and becomes the fragment's latest revision, which every machine importing the fragment without a pinned version picks up, so be sure the user wants the change, and read the fragment with read_fragment_config first. Given the fragment id, finds the item with the given name — a component, service, registry_module, remote, trigger or job, or a fragment import named by the imported fragment's id (pass prefix when that fragment is imported more than once); pass item_type when the name fits items of two types, and a registry module may be named by its module id — and merges patch into it. patch holds only the fields to change, with JSON Merge Patch semantics: objects merge key by key, a null value deletes that key, and arrays and other values replace the current one whole, so to change one element of an array pass the whole new array. What identifies an item cannot be patched — a fragment import's id and prefix, a module's module_id, a component's or service's api (or pre-api type) and model: delete the item and add another instead. The result shows the item as saved and as it was. This tool only changes an item that exists: it never adds or removes one. |

| `call_machine_api` | Live machine (destructive) | Call one method of a Viam API on a live machine and return its response: the structured component and service APIs (`https://docs.viam.com/reference/apis/`), such as GetReadings on a sensor, MoveToPosition on an arm or GetPosition on a base, and the machine-level methods of rdk:robot:robot, such as GetMachineStatus. Given the machine id (from list_machines), the resource's name (from read_machine_config, with any fragment prefix; pass api too when two resources share the name, and omit resource_name for a machine-level method), the method's RPC name and its request as protobuf JSON (field names as in the proto, snake_case or lowerCamelCase; the resource name field is filled in for you), this connects to the part and calls the method at once: there is no preview and no undo, and a method can move hardware, so tell the user what you are about to call and get their go-ahead first. The call runs in a session that ends with it, so continuous motion it starts (a motor's SetPower or SetRPM, a base's SetPower or SetVelocity) stops a moment after it returns; for a move that should complete use a bounded method such as GoFor, GoTo, MoveStraight or Spin. Only unary methods can be called. An image in the response, such as from a camera's GetImages or a vision service's CaptureAllFromCamera, is taken out of the JSON, scaled down to at most 1568 pixels a side, listed in images and attached to the result as a picture you can see; a raw or depth frame cannot be shown, so where a camera offers a choice of format ask for image/jpeg or image/png. The rest of the response must fit in 64 KB, so a point cloud is refused. The part must be online, and the user must be allowed to control the machine. For a model's own free-form commands use run_docommand instead. |
| `run_docommand` | Live machine (destructive) | Run a DoCommand on one of a live machine's components or services and return its result. DoCommand is the free-form command channel a resource's model may implement: the command object and the result are whatever the model defines, so read the model's documentation with get_registry_item_information (its README usually lists the commands) or ask the user before guessing one. Given the machine id (from list_machines), the resource's name (from read_machine_config, with any fragment prefix) and, on a multi-part machine, the part it is on, this connects to the part and runs the command at once: there is no preview and no undo, and a command can move hardware, so tell the user what you are about to run and get their go-ahead first. The part must be online, and the user must be allowed to control the machine. For a standard API method such as GetReadings or MoveToPosition use call_machine_api instead. |
